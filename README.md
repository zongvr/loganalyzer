## 一、选题说明

- **题目**：`loganalyzer` —— 一个轻量命令行日志分析工具。读取本地日志文件，统计各级别（INFO/WARN/ERROR）出现次数，支持按时间区间 / 关键字过滤、Top N 高频错误、文本表格与 JSON 两种输出格式。
- **选题理由**：
  1. 需求边界清晰、可完整落地，符合「轻量、可交付」要求；
  2. 天然可拆成多轮迭代（读文件 → 解析级别 → 过滤 → 格式化 → 性能 → 异常 → 测试 → 重构 → 容器化 → 文档），每一轮都能体现「指令→代码变更→提交」的闭环；
  3. 可用 Docker 容器化，呼应岗位对容器 / Linux 能力的要求，形成差异化。
- **环境准备说明**：仓库初始化、`go.mod`、`.gitignore`、本 README 模板、`tools/gen_jsonl.py`、目录骨架由候选人在使用智能体前完成（属于工程脚手架，**不计入智能体交互轮次**）。JSONL 的 `round_id` 从第一次 Kilo Code 功能交互（第 1 轮）开始编号。

## 三、提示词（Prompt）产生的方法

> 本节说明我如何把业务需求转化为给 Kilo Code 的指令，供评审参考。

这套方法论并非一开始就想好的，而是在前 4 轮的实际踩坑中逐步固化下来的：

1. **先拆后问**：把一个大需求拆成最小可验证单元，每轮只给一个明确目标，避免一次性大指令导致难以 review。
   每轮结束后 `git diff` 应当只有一个文件、一个主题——diff 越干净，JSONL 的「一一对应」越经得起对照。
2. **给上下文不替写**：指令里说明「现有结构与意图」，但让智能体产出实现，我再审核 diff。
3. **缺陷指令三要素**：当指令的目的是修 bug 时，必须给全三样——① 可复现的最小命令 + 实际输出与期望输出对比；
   ② 已定位到的根因；③ 候选方案及取舍依据。只说「这里有问题你改一下」，智能体大概率会改错方向。
   round 2、round 4 的提示词都按此结构编写。
4. **可验证性 + 不采信自述**：每条指令都附带可执行的自测清单（命令 + 预期输出）。
   但关键在于——**清单由我本人复跑，不接受智能体代填结果**。
   round 3 中 Kilo Code 声称「已验证 `3+3+5+2+4=17`」，实际运行结果是 `4+2+5+2+4=17`：
   求和恰好正确、分项却是错的（详见第五节问题 2）。自此在提示词中固定写明
   「自测清单我会逐条复跑，请勿代填结果」。
5. **预判高频缺陷并前置堵住**：针对已知的语言级陷阱，在指令里提前立约束，而不是等它写错再返工。
   例如 round 3 明确要求「输出顺序必须由固定切片控制，不得依赖 map 遍历顺序」——
   Go 的 map 遍历是随机的，这是此类代码的经典坑。
6. **给出可校验的不变式**：让智能体拿到一个能自我检查的等式，例如
   `ERROR + WARN + INFO + DEBUG + UNKNOWN ≡ Total lines`。
   但需注意：**不变式只能证伪不能证实**——round 3 的虚构数据恰好满足该等式却仍是错的，
   所以不变式是辅助手段，不能替代实跑。
7. **重构 / 性能类改动一律用差分测试验收**：这类改动的正确性判据不是「新用例通过」，
   而是「**行为与改动前逐项一致**」。做法是从 git 取出上一轮的代码单独编译成基线二进制
   （`git show <prev>:cmd/loganalyzer/main.go`），用同一批语料跑两版并比对输出。
   round 4 的性能优化通过了全部既有用例与内存指标，却把中文日志的分词改坏了——
   正是靠与 round 3 基线差分才抓到（详见第五节问题 4）。
8. **针对本地化场景专门造料**：纯 ASCII 测试集永远测不出编码相关缺陷。
   涉及字符串切分、大小写、宽度对齐的改动，必须补一组中文 / 多字节语料
   （本项目为 `testdata/utf8_edge.log`）。
9. **逐步加约束**：先跑通主路径，再叠加错误处理、性能、格式等约束，符合「可完整落地」原则。
10. **压制话痨**：明确要求「不要在对话里粘贴完整代码或 diff，只说实现思路」。
    diff 我从 `git diff` 拿最准确，也能节省智能体的上下文窗口给真正的推理。

（每轮实际使用的 `prompt_content` 见 `AI开发考核_刘贵达_loganalyzer.jsonl`，
提示词原文另存于 `prompts/round-N.md`。）

## 四、JSONL 文件的生成方法

1. 每一轮用 Kilo Code 完成改动并**经我复测通过**后，立即提交：
   ```bash
   git add cmd/loganalyzer/main.go        # 只 add 本轮实际改动的文件
   git commit -m "round N: <本轮目标>"
   ```
   **刻意不使用 `git add -A`**：工作区常混有提示词草稿、测试数据、工具脚本等无关改动，
   一旦被卷进 `round N` 提交，该轮 `modify_diff` 就不再纯粹对应智能体的这次修改，
   「一一对应」也就失真了。无关文件一律用单独的 `chore:` 提交分离出去。
2. 在 `rounds.json` 中追加该轮记录，只需填 5 项：`round_id` / `prompt_content`（真实发出的指令原文）/
   `commit_hash` / `agent_type` / `dev_language`。
   其中 `prompt_content` 由脚本从 `prompts/round-N.md` 中精确抽取，避免手工复制引入转义错误。
3. 运行生成器自动补全 `modify_diff` 与 `modify_time`（两者均取自真实 git 历史）：
   ```bash
   python3 tools/gen_jsonl.py \
     --repo . \
     --rounds rounds.json \
     --out "AI开发考核_刘贵达_loganalyzer.jsonl"
   ```
4. 输出文件编码 UTF-8（无 BOM）、每行一条 JSON、无空行、无注释，符合考核规范第三部分。
5. 每次生成后运行合规校验，逐条核对：字段齐全且顺序一致、无多余字段、`round_id` 连续递增、
   `modify_diff` 与 `git diff <hash>^ <hash>` **逐字节一致**、`modify_time` 与 commit 时间**完全一致**。

> **设计要点**：`modify_diff` 与 `modify_time` 全部由脚本从 git 真实历史抓取，**从机制上排除了编造与篡改的可能**——
> 这也是本项目**不让智能体代写 JSONL** 的原因：智能体拿不到本地真实的 commit 哈希与 diff，
> 若让它"帮忙整理"，它只能凭推测填充，而这恰好会踩中考核「不得篡改指令与 diff 记录」的红线。
> 需人工保证的仅两项：`prompt_content` 为真实发出的指令、`commit_hash` 对应当轮提交。

## 五、过程中遇到的问题和解决方法

> 按轮次如实记录，包含 Kilo Code 生成代码的缺陷、我如何发现与定位、以及如何转化为下一轮修复指令。

### 问题 1：`bufio.Scanner` 单行 64KB 上限导致超长行崩溃（round 1 → round 2）

- **发现方式**：round 1 的代码通过了 `go vet`、`gofmt`、正常文件、缺参数、文件不存在等全部常规用例。
  但我没有止步于「跑通即通过」，而是**主动构造边界用例**——生成一个含 10 万字符单行的日志文件：
  ```bash
  python3 -c "open('/tmp/longline.log','w').write('A'*100000 + '\n' + 'short\n' + '\n')"
  ./loganalyzer --file /tmp/longline.log
  ```
- **现象**：程序报错退出，`错误：读取文件失败：bufio.Scanner: token too long`（退出码 1）。
  期望应为 `Total lines: 3 / Empty lines: 1`。
- **定位**：`bufio.Scanner` 的单个 token 默认上限是 `bufio.MaxScanTokenSize`（64KB）。
  这**不是钻牛角尖的边界**——生产日志中的长 JSON 请求体、Java 异常堆栈单行超过 64KB 极为常见，
  属于会在真实环境直接导致统计失败的**生产级缺陷**。
- **转化为修复指令**：我在 round 2 的提示词中提供了三要素——① 可复现的最小命令与实际/期望输出对比；
  ② 已定位的根因（`bufio.MaxScanTokenSize`）；③ 两个候选方案及取舍依据：
  - **方案 A**：`scanner.Buffer()` 扩容上限——缺点是仍需硬编码一个可能仍不够的上限值；
  - **方案 B**：改用 `bufio.Reader` + `ReadString('\n')`——天然无单行长度上限。

  同时给出边界约束：必须保持流式（内存不随文件总大小增长）、末行无换行符仍需计数、空文件输出 0/0 且退出码 0。
- **结果**：Kilo Code 选择了**方案 B**，并正确处理了 `io.EOF` 时最后一段无换行内容的计数。
  我复测了 10 项用例（含原 bug 用例、空文件、末行无换行、仅一个换行、CRLF 行尾、目录、无权限文件）全部通过；
  另做 10MB 单行压测：耗时 0.03s、峰值常驻内存 24MB，证明内存只随**单行长度**增长而非文件总大小，流式特性未被破坏。
- **复盘**：这一轮验证了「AI 生成的代码能跑通 ≠ 代码可用」。评审真正该看的是**审核者是否具备构造边界用例、
  定位根因、并把根因转化为精准修复指令的能力**——而不是 AI 一次写对的运气。

### 问题 2：智能体自称「已验证」，但给出的验证数据是虚构的（round 3）

这是本项目中**最值得警惕**的一次发现，与代码缺陷无关，而与协作方式有关。

- **现象**：round 3 完成后，Kilo Code 在交付摘要中写道：

  > 已验证不变式：17 行样例 `3+3+5+2+4 = 17 = Total`；空文件全 0、退出码 0。

  该数字对应 `ERROR 3 / WARN 3 / INFO 5 / DEBUG 2 / UNKNOWN 4`。

- **实测结果**：我编译后实际运行 `./loganalyzer --file testdata/sample.log`，输出为
  `ERROR 4 / WARN 2 / INFO 5 / DEBUG 2 / UNKNOWN 4`。**ERROR 与 WARN 各差 1。**

- **人工核对**：逐行手工判定 17 行样本，`ERROR` 出现在第 5、8、12、16 行（其中第 8 行是小写 `error`），
  共 4 行；`WARN` 出现在第 4、11 行（其中第 11 行是小写 `warn`），共 2 行。
  **实际程序输出正确，是智能体的自述数据错误。**

- **为什么这个错误极具迷惑性**：它给出的 `3+3+5+2+4` 求和**恰好也等于 17**，与我在提示词中要求校验的
  不变式 `ERROR+WARN+INFO+DEBUG+UNKNOWN ≡ Total` 完全吻合。如果只核对"总和对不对"，
  就会认为验证已通过而放行。**分项数字与真实输出不符这一点，只有实际运行程序才能发现。**

- **定性**：智能体并未真正执行编译与运行，而是**基于代码逻辑推演出一个"看起来自洽"的结果**，
  并以"已验证"的措辞呈现。这属于 AI 协作中的典型风险——不是代码错，是**过程陈述不可信**。

- **应对**：确立一条固定纪律并沿用至后续所有轮次——
  **智能体给出的任何"已验证 / 已测试 / 结果正确"的自述，一律不予采信，全部由我本人重新编译、
  重新运行、逐条比对输出。** 提示词中也相应加上「自测清单我会逐条复跑，请勿代填结果」的约束。

- **复盘**：这次的教训比问题 1 更深一层。问题 1 说明"AI 写的代码要审"，
  问题 2 说明"**AI 说它审过了，这句话本身也要审**"。在把智能体产出纳入正式交付的场景里，
  可复现的验证证据（真实终端输出、真实 git diff）必须取代自然语言承诺——
  这也正是本项目坚持用脚本从 git 真实历史自动抽取 `modify_diff` 与 `modify_time`、
  而不让智能体代写 JSONL 的根本原因。

### 问题 3：`classifyLevel` 只需前 3 个字段，却切分了整行（round 3 → round 4）

- **发现方式**：round 3 的功能验证全部通过后，我补做了一组**对照压测**——
  构造两个体积完全相同（均为 4MB）、但字段数量差异极大的单行文件：

  ```bash
  python3 -c "open('/tmp/fewfields.log','w').write('X'*4000000+'\n')"          # 1 个字段
  python3 -c "open('/tmp/manyfields.log','w').write(('x '*2000000).strip()+'\n')" # 200 万个字段
  /usr/bin/time -l ./loganalyzer --file /tmp/fewfields.log
  /usr/bin/time -l ./loganalyzer --file /tmp/manyfields.log
  ```

- **现象**：

  | 单行内容 | 字段数 | 峰值常驻内存 |
  |---|---|---|
  | 4MB 连续字符 | 1 | 11.5 MB |
  | 4MB `x x x ...` | 2,000,000 | 43.7 MB |

  文件大小相同，**仅因字段数暴增，内存涨至 3.8 倍**。

- **定位**：`classifyLevel` 中使用了 `strings.Fields(line)` 再 `fields[:3]`。
  `strings.Fields` 会先把**整行所有字段**切出并分配完整切片，之后才丢弃第 3 个之后的部分——
  函数实际只需要前 3 个字段，却为整行付出了内存代价。这与 round 2 确立的
  「内存不随输入规模无谓增长」的流式原则相违背。

- **性质**：这是**非功能性缺陷**——不会报错、不会算错，所有功能用例都能通过，
  只在极端输入下表现为资源退化。它无法通过常规功能测试暴露，只能靠压测与对照实验发现。

- **同时发现的格式缺陷**：级别统计输出使用 `fmt.Printf("  %-7s %d\n", ...)`，
  但最长标签 `UNKNOWN:` 有 8 个字符，超出宽度 7 而不被填充，导致该行数字列错位、与其余四行不对齐。

- **转化为修复指令**：round 4 提示词中同时给出两处修复要求，并附上上述对照实验数据作为依据；
  明确约束「切分口径必须与 `strings.Fields` 一致」「级别优先级语义不得改变
  （前 3 字段为 `INFO x ERROR` 时须判为 `ERROR`）」，防止为优化而引入行为变化；
  另要求把 `type Stats struct` 移到 `analyze` 之前（原定义在使用者之后，阅读需向下跳转）。

- **解决（round 4）**：智能体改用手动逐字符扫描收集字段、取满 3 个即 `break`，不再为整行分配切片；
  输出宽度改为遍历 `levelOrder` 动态计算最长标签后用 `%-*s` 格式化。复测结果：

  | 单行内容 | 字段数 | round 3 峰值内存 | round 4 峰值内存 |
  |---|---|---|---|
  | 4MB 连续字符 | 1 | 11.5 MB | 11.7 MB |
  | 4MB `x x x ...` | 2,000,000 | 43.7 MB | **11.5 MB** |

  内存退化消失，对齐修复，两个目标均达成。**但这次修复本身引入了一个新缺陷，见问题 4。**

### 问题 4：性能优化引入 UTF-8 分词回归，中文日志级别误判（round 4 → round 5）

- **发现方式**：round 4 的全部既有用例（功能 + 边界 + 异常 + 内存指标）都通过了。
  但我注意到新实现用 `unicode.IsSpace(rune(line[i]))` 逐**字节**判定空白，
  而 `line[i]` 是 byte、`rune(line[i])` 并非 UTF-8 解码，遂**专门构造中文语料做差分测试**——
  以 round 3 版本（`strings.Fields`，语义已知正确）为基线，逐项比对两版输出。

- **现象**：语料 `testdata/utf8_edge.log`（8 行，级别均位于前 3 字段内）：

  | | ERROR | WARN | INFO | DEBUG | UNKNOWN |
  |---|---|---|---|---|---|
  | 正确期望 | 4 | 1 | 2 | 1 | 0 |
  | round 3（基线） | 4 | 1 | 2 | 1 | 0 ✅ |
  | **round 4** | **2** | 1 | **1** | 1 | **3** ❌ |

  8 行错 3 行，错误率 37.5%，全部错在含汉字 `堀` 的行上。

- **根因**：UTF-8 多字节序列的续字节落在 `0x80~0xBF`；而 `unicode.IsSpace` 在 Latin-1 区间
  认定 `U+0085`（NEL）与 `U+00A0`（NBSP）为空白字符——**这两个值恰好落在续字节范围内**。
  于是：

  - `堀` = `E5 A0 80`，中间的 `A0` 被误判为分隔符 → 一个汉字被劈成两个"字段"，
    把真正的级别 token 挤出前 3 字段 → 判为 `UNKNOWN`；
  - `习` = `E4 B9 A0`，`A0` 在末尾，恰好只起分隔作用、字段数不变 → **侥幸判对**。

  即：是否出错取决于 `0xA0`/`0x85` 落在多字节序列的**哪个位置**，具有隐蔽的偶发性。

- **性质**：这是**性能优化改坏语义**的典型案例。它绕过了所有既有测试——
  功能用例是纯 ASCII 的、边界用例是长度/换行维度的、内存用例只看资源指标，
  三类测试都不会碰到「非 ASCII 字符 + 字节级空白判定」这个交叉点。

- **为什么能抓到**：靠的不是新增用例，而是**拿上一版做基线做差分比对**。
  性能优化类改动的正确性判据应当是「行为与优化前逐项一致」，而非「新用例是否通过」。
  这条纪律已固化进第三节提示词方法论。

- **转化为修复指令**：round 5 提示词给出复现语料与三方对照表、逐字节拆解根因，
  并给出两个候选方案（A：只认 ASCII 空白，按字节扫描安全但语义略有差异；
  B：`utf8.DecodeRuneInString` 正确解码后判定，与 `strings.Fields` 完全等价），
  同时设置硬性约束——**禁止退回 `strings.Fields`**（否则内存退化复发）、
  必须保留提前 `break`、级别优先级语义不变、本轮只改 `classifyLevel`。
  验收判据明确为「与 round 3 基线差分一致」。

- **复盘**：问题 1 是「AI 写的代码要审」，问题 2 是「AI 说它审过了，这句话也要审」，
  问题 4 则是第三层——**「AI 修好了一个缺陷」这件事本身，也可能带来新的缺陷**。
  三者共同指向同一条纪律：每一轮的验收都必须**以上一轮的既有行为为基线**，而不是只验证本轮新目标。

- **修复结果（round 5，commit `08ca8f5`，已复测）**：采用**方案 B**——
  `classifyLevel` 用 `utf8.DecodeRuneInString` 逐 rune 正确解码后交 `unicode.IsSpace` 判定空白，
  与 `strings.Fields` 语义完全等价，同时保留「扫描到第 3 字段即停止、不为整行分配字段切片」的内存优化。
  **本人独立差分复跑**（不采信 AI 自述）：当前版与 round 3 基线（`04d58ee`）在
  `utf8_edge.log` / `sample.log` / `test.log` / 空文件 / 10 万字符长行 / 末行无换行等语料上
  **级别统计数值逐项一致**；`utf8_edge.log` 输出 `ERROR 4 / WARN 1 / INFO 2 / DEBUG 1 / UNKNOWN 0`
  （与 round 3 基线一致，而 round 4 基线在此为 `ERROR 2 / UNKNOWN 3`），**UTF-8 回归已修复**。
  注：输出对齐沿用 round 4 的动态列宽（round 3 为固定 7 宽且 UNKNOWN 列曾错位，属已修复缺陷，不回退），
  故逐字节 diff 仅在填充空格上有差异，级别计数零差异。

### 6.3 当前已实现的用法

```bash
# 唯一参数 --file（必填）：统计总行数、空行数与日志级别分布
./loganalyzer --file testdata/sample.log

# 查看帮助
./loganalyzer --help
```

预期输出（以仓库自带的 17 行样本为例，为 `./loganalyzer --file testdata/sample.log` 的真实输出，逐字符一致）：

```
Total lines: 17
Empty lines: 1

Level statistics:
  ERROR:   4
  WARN:    2
  INFO:    5
  DEBUG:   2
  UNKNOWN: 4
```

> 级别标签列宽由程序在输出前按最长标签动态计算（见问题 3 的对齐修复），因此新增级别也不会错位。

**级别判定规则**：取每行前 3 个空白分隔字段，逐字段 `ToUpper` 后精确匹配，
按 `ERROR > WARN > INFO > DEBUG` 优先级取第一个命中；均未命中记为 `UNKNOWN`。
恒等式 `ERROR + WARN + INFO + DEBUG + UNKNOWN ≡ Total lines` 始终成立，可用于自校验。

### 6.4 退出码约定

| 退出码 | 含义 |
|---|---|
| 0 | 正常完成（含空文件，输出全 0） |
| 1 | 未传 `--file` / 文件不存在 / 无读权限 / 传入的是目录 / 读取过程出错 |

错误信息统一输出到 stderr，均为中文友好提示。

## 七、Git 提交规范

### 7.1 提交类型：只有 `round N:` 计入智能体轮次

本仓库的提交分为两类，请评审据此对照 JSONL：

| 前缀 | 含义 | 是否计入 JSONL |
|---|---|---|
| `round N: <目标>` | 一次完整的智能体交互（我下指令 → Kilo Code 改代码 → 我审核验证） | **是**，与 `round_id` 一一对应 |
| `chore: <说明>` | 环境准备、提示词定稿、JSONL 归档、README 补写等**非智能体产出**的内容 | 否 |

之所以严格拆开，是为了让每个 `round N:` 提交的 diff **只包含智能体真正修改的源码**。
因此每轮提交一律使用 `git add cmd/loganalyzer/main.go` 精确添加，**刻意不使用 `git add -A` / `git add .`**——
后者会把提示词文件、JSONL、README 改动一并卷入，`modify_diff` 就不再是「这一轮 AI 改了什么」的干净证据。

### 7.2 提交历史的完整性承诺

- 全程仅使用 `add` / `commit` / `push`，**从未使用** `rebase`、`reset`、`amend`、`squash`、`filter-branch` 等任何会改写历史的操作。
- 单一 `main` 分支，线性历史，**零合并提交**（可用 `git log --merges` 验证，输出为空）。
- 已写入 JSONL 的提交哈希永久有效，不会因后续操作而失效。

### 7.3 关于首个提交的作者署名（如实说明）

`git shortlog -sne` 会显示两个作者名：

```
    12  刘贵达 <26046710@qq.com>
     1  Candidate <26046710@qq.com>
```

其中署名为 `Candidate` 的仅有**初始化提交 `66b73df`**（`chore: 初始化仓库与工具链`），
原因是搭建脚手架时先用了占位署名，随后即改为真名，后续 12 个提交均为「刘贵达」，**邮箱自始至终一致**。

**为什么不修正它**：修改历史作者需要 `git rebase` 或 `git filter-branch`，这会重写该提交之后**所有** commit 的哈希值，
导致 JSONL 中已记录的 5 个 `commit_hash` 全部失效，同时违反考核「提交历史必须完整可追溯、不得篡改」的要求。
两害相权，**保留痕迹并如实说明，优于为了好看而破坏可追溯性**——这也是本项目一以贯之的原则。
